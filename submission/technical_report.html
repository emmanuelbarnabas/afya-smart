Afya Smart — Technical Report

AI-powered triage & queue management for fairer, faster public healthcare

Competition: RIDC PT Innovation Hackathon 2026 · Category: Software (Web & Mobile)
Author: Emmanuel Stephen Barnabas · Repository: github.com/emmanuelbarnabas/afya-smart
Stack: Python (FastAPI), SQLAlchemy, Alembic, SQLite/PostgreSQL, scikit-learn gradient boosting (joblib), Africa's Talking (USSD + SMS), React dashboard + vanilla-JS PWA, Cloudflare tunnel
Status: Working end-to-end prototype · 107 automated tests passing
Prototype notice. This is a hackathon prototype and is not for real clinical use. The triage rules and model must be reviewed and signed off by medical professionals before any real patient is triaged by this software. This warning is repeated inside the USSD menus and the nurse dashboard.

1. Problem & approach

Public clinics in Tanzania face long, opaque queues and no triage before arrival: a stroke case and a prescription refill wait in the same line. Existing digital-health tools assume smartphones and data bundles, excluding the majority of patients who use 2G feature phones. Waits also vary systematically by sex, age and patient type — unmeasured, therefore unfixed.

Afya Smart moves triage and booking before the visit, on the channel everyone already has: USSD. A patient dials *384#, answers a short symptom interview in Kiswahili or English, receives a RED / YELLOW / GREEN urgency level with a reason, and books the first free slot at a chosen facility. The nurse sees one live queue per facility; a fairness report makes wait disparities visible.

2. System architecture

A single FastAPI service exposes a versioned JSON API (/api/v1), serves the static web front-ends (nurse dashboard, patient PWA, USSD simulator, demo landing), and handles the Africa's Talking USSD callback. The same SQLAlchemy models run on SQLite (demo/offline) and PostgreSQL (production) via Alembic migrations.

  • Channels: USSD (Africa's Talking callback), patient PWA (installable, works offline-first), nurse web dashboard, walk-in/anonymous intake at the facility desk.
  • Core services: intake, triage, booking (slots/appointments), queue, reminders (SMS with dedup), forecasting (slot demand), analytics, notify.
  • Intelligence: rule-based red-flag safety net + gradient-boosting urgency classifier (model version ml-v2), loaded in-process via joblib with rules-only fallback.
  • Deployment: uvicorn behind a Cloudflare tunnel for a public HTTPS URL; no external queue broker or cloud DB required.

3. AI triage engine

The triage pipeline is deliberately conservative — safety first, ML where it helps:

  • Feature extraction. Free-text symptom description (Kiswahili/English) → keyword/phrase features, plus age and duration.
  • Rule-based red-flag layer. Deterministic detection of emergencies (chest pain, stroke signs, severe bleeding, breathing difficulty, high fever in infants, etc.). This layer always overrides the model; if rules and model disagree, the safer outcome wins.
  • ML classifier. Gradient boosting trained on 12,000 synthetic-but-clinically-shaped symptom profiles. Reported metrics (ml-v2, held-out set): overall accuracy 89.4%, emergency recall 88.4%. Every prediction is stamped with model version and reason for auditability.
  • Clinician feedback loop. After consultation the nurse records the real urgency (queue_entries.clinician_urgency, triage_sessions.clinician_urgency). Prediction-vs-actual disagreement is retained for periodic retraining — the model is designed to improve from the people it assists.
  • Graceful degradation. If the model file fails to load, the API reports it in /api/v1/health and serves rules-only triage rather than failing the session.

4. Fair queue engine

Queue order is urgency-banded FIFO with an ageing override: priority = urgency_weight × 60 − minutes_waited, so a GREEN patient who has waited long can overtake a fresh YELLOW arrival without ever overtaking RED. Emergency bypasses are allowed but individually flagged and auditable. Patients receive SMS reminders (one per appointment, dedup-guarded by reminder_sent_at) and can track their live position from the PWA or USSD menu My appointments.

5. Fairness & accountability

The fairness report (/fairness) computes average and 90th-percentile waits grouped by sex, age band, facility, urgency level and walk-in vs booked. Group gaps are surfaced explicitly so staff and patients can see bias, and clinic policy can be corrected with evidence. Nurse urgency overrides are stored with actor and timestamp, keeping the human decision auditable.

7. Verification & testing

  • 107 automated tests passing (pytest) covering triage rules, ML behaviour, USSD state machine (both languages), queue fairness logic, booking/reminders, and API endpoints.
  • Live USSD wiring verified against the Africa's Talking sandbox callback; SMS dedup verified by repeated reminder runs.
  • Model health exposed at /api/v1/health: loaded flag, version, algorithm, trained_at, accuracy and emergency recall.

9. Limitations & next steps

  • Triage rules are not clinically validated. Medical sign-off is a stated prerequisite for any real deployment.
  • Training data is synthetic. Real symptom phrasing (dialects, code-switching) will shift feature distributions; the feedback loop exists precisely to collect the real signal.
  • Reminder delivery is SMS-only; IVR/WhatsApp channels and delivery-receipt reconciliation are planned.
  • Single-facility queue focus; cross-facility referral hand-off is roadmap work.

Next steps: 90-day pilot with 2–3 public dispensaries, clinical review board for the rules, then retraining on clinician-confirmed labels and TMDA / data-protection compliance work.
